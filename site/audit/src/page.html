The six function groups

A group says what kind of code an edit touches, and so what an install must refresh.

GroupWhat it isHow an edit to it is installed
OPBody of a per-call Python functionSwap the Python function or object in place
GRAPHCode inside a CUDA graph or torch.compile regionSwap, then selectively re-trace or recapture the affected compiled graphs
STATEObjects built once at start (buffers, runners, batch builders)Swap, then rebuild the pre-allocated buffers, runners or tables it touches
RESOURCELoad-time memory layout and allocationAllocate new, copy, switch, free
RANKSAnything all GPUs must agree onAny of the above, committed on all ranks or none
NATIVECUDA/C++ kernel sourceCompile into a versioned shared library, rebind the op, recapture
restartNot a group: startup logic, launch flags, environment variablesRefused; needs a restart

Transaction rules

phase 1, steps go on:   prepare on every participant (stage beside the old state, check, vote)
phase 2, one step gap:  validate on every participant (staged code still current)
                        -> commit on all, or abort on all
                        -> a commit that fails undoes the committed ones in the same gap
  • Three outcomes. committed (all switched), aborted (none switched), rolled_back (switched and undone in the same gap).
  • Participants. Worker ranks (quiesce between two steps), the engine core (inside its busy loop, between steps) and the API server (between requests; not in the kernel yet). "Every participant call returns {"ok": bool, ...} and never raises; a crash or a malformed reply counts as not-ok."
  • A caller that times out asks, never assumes. status(id) answers prepared, committed, aborted, undone or in-doubt.
  • Undo is exact for code, not for data. "The journal restores the same code and attribute objects and removes every name it added." Data the new code wrote needs the plan's undo resets: drain, cache clear, snapshot revert.
  • Checks advise. Every check returns a finding, never an exception. The caller's accept list decides, and only overridable findings can be accepted. Physical limits cannot: patch_invalid, no_live_function, closure_changed, empty_change, participant_failed, tampered, session_poisoned and the rest of the catalog.
  • Deleting a definition is an edit (removed_definition), and "an edit that changes no code is refused" (empty_change).
  • Poison. The lab records a code fingerprint per participant. It is poisoned by "a fingerprint that differs (code changed outside the journal), a crash, a hang, a lost participant, a failed undo or rollback, an unresolved in-doubt transaction, a participant that missed the phase-2 deadline". A poisoned lab refuses install with session_poisoned until reset("respawn").
  • Receipts. "Written by one shared writer, never by engine code or agents." A transaction leaves linked txn, proof and undo records that share its id. The writer "needs a human owner" before its receipts count.

Witness rules

  • "Witness proves that swapped code ran, per participant." The swap puts a counter call at the top of each new function body.
  • "A swap that never ran is never a pass." Zero live calls is running_frame when a frame of the old code is still running, else zero_witness (not reached). The check then reads proven: False.
  • Capture is not a run. Calls made while the engine captures a graph "prove capture, not a run", so they are counted apart.
  • No witness, no proof. A transaction whose witness has no key at all is a no_witness_possible finding at proof.
  • The witness hook is never deleted. "Code compiled or captured while an edit was installed may still call it. Undo binds a no-op stub."
  • For agents: "A check counts only if it says the patched path ran."

Rules for agents and for the kernel

Skill rules (the agent using a lab)

  • Before every experiment, read the engine's knowledge base: probes, their cost, reset rules, unsupported paths.
  • "Pick the cheapest probe that still runs the code you changed."
  • Send a promising result to the full evaluation asynchronously and keep working.
  • "On poisoned, or when the cost hook says a call restarted, do not keep measuring on that lab."
  • "A check counts only if it says the patched path ran."
  • "A result counts only with the lab's receipt. Never write or edit one."
  • Slow check, failed install or an uncovered module: call the online toolsmith.

core/agents/livelab_overview.md

Toolsmith principles, offline

  • "Prove it offline, check cheaply online." Every guarantee should be settled once, at toolsmith time.
  • "Prefer a design that makes the bad case impossible over a check that detects it."
  • "Prove each such design once with a test that tries the bad case and must fail."
  • "Keep an online check only if it is small", and say its cost next to it.
  • "Every component reports its own time."
  • Stay inside one engine: "Do not invent cross-engine abstractions."
  • Verify each tool with base → edit → injected fault → reverted base, compare against a fresh process, then pass conformance.
  • In the knowledge base, "every number cites how it was measured."

core/agents/toolsmith_offline.md

Toolsmith principles, online

  • Before a new kind of experiment, price it in writing: the restart class and state pollution, the predicted cost, and the cheapest probe.
  • "A difference smaller than that noise needs repeats, not one run per point."
  • Do not become overly conservative: when a structural edit is better, "price the necessary component or engine restart honestly and take it."
  • Extend coverage "with the smallest concrete mechanism that works for this engine".
  • "Verify the new or changed tool against a fresh process before handing it back."

core/agents/toolsmith_online.md

Kernel invariants

  • "Nothing raises to the caller." A failure is a finding.
  • "Checks advise." A check returns a finding; the caller's accept list decides.
  • "Undo is exact for code, not for data."
  • "Attributes outside __dict__ go through getattr / setattr."
  • "The heap scan unfreezes the gc." The scan yields the interpreter lock in slices.
  • "The witness's frame check stays cheap." It walks thread stacks and does not scan the whole heap.

The 11 conformance cases

"A lab's receipts count only after it passes every case." Each case drives a lab only through the five verbs plus a small test harness.

CasePasses only if
c0_repeatableThe workload gives the same output when nothing changes.
c1_noopA change that keeps behavior installs, runs (witness), and leaves output bit-exact.
c2_visibleA visible edit changes output, and the witness fires on every participant.
c3_fresh_equivalenceThe live edit's output equals a fresh process started with that edit.
c4_uninstallUndo returns output and code identity to base.
c5_failed_installA fault in the middle of an install leaves base, proven.
c6_refusalUnsupported edits are refused with the right code, and nothing changes.
c7_chainStacked edits each run; undoing them one by one returns each earlier output exactly.
c8_crash_and_hangCrash, hang, lost participant and tampered code each poison the session; respawn returns to base.
c9_soakOutput returns to base after repeated cycles of install and undo.
c10_not_provenAn edit that never runs installs, but its check reads proven: False with zero_witness.
