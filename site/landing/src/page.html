Self-improvement is a loop, and evaluation increasingly dominates it

An agent edits the system, evaluates the edit, keeps it if it helped, and goes again. Every turn of the loop waits on the evaluation. That wait has two parts, and FastRSI goes after both.

Wait, where does the overhead come from?

Think about how you would debug one line in a model server yourself. Scroll to try it three ways.

From a terminal

Edit one line. Restart everything.

This is how most agents check an edit today. The engine reloads its weights, recaptures CUDA graphs and re-tunes kernels before it runs a single benchmark step.

On vLLM that is 228 s per try, and 88% of it is start-up. If the idea was wrong, you pay it all again.

Yeah, I know. Super slow, right?

From a notebook

Keep the engine alive.

One hacky way to preserve the state: move everything into a Jupyter notebook, if that is possible at all. Load the engine once, edit the file, reload the one module you changed, and run just a few steps, enough to tell whether the idea works.

A try now takes 2.4 s. This is the best case: nothing is cheaper than editing an engine that is already warm.

The catch

Until a reload lies to you.

Hot reload by hand is fragile, and it does not last. Sooner or later a number looks great and you can't trust it.

stale objectsstale graphsdirty state✗ fragile: restart to be sure

FastRSI, part one

Make the notebook trick safe.

FastRSI keeps the notebook's speed and adds a safety net. Each edit is a transaction that takes the cheapest path that is still safe, and falls back to the next one when it has to.

  1. Install into the live enginecheapest
  2. Rebuild only what the edit touched
  3. Respawn from a warm copy
  4. Full restartlast resort

A bad edit fails its check and is reverted. The engine survives it.

FastRSI, part two

Probe to steer. Evaluate in full to confirm.

While developing, you rarely need the whole benchmark. The agent writes a targeted probe: a few steps on the code path it just changed.

The full evaluation still runs on the edits worth keeping. It can run in the background, so the agent is never blocked on it.

FastRSI prepares an engine once, then improves it live

An offline toolsmith turns the engine into a live lab once. A developer agent then improves the engine inside that lab. Play the six steps, or click one.

Stage 1 · offline

Sort every function by what an edit to it disturbs.

The offline toolsmith reads the codebase, its past PRs, issues and tests. It sorts functions into six groups. Each group has its own way to install an edit without a restart.

Only start-up logic, launch flags and environment variables still need one.

Stage 1 · offline

Build what the engine lacks.

Each engine needs different machinery to stay warm: a process to fork from, weights held outside the worker, a saved start state to return to. The toolsmith builds these per engine and records what each one costs.

Stage 1 · offline

Prove each tool against a fresh process.

Every tool is checked the same way: base, edit, injected fault, reverted base, each compared with a cold start. A lab's results count only after it passes all 11 conformance cases.

The guarantees are settled here, offline, so the checks that run on every edit can stay small.

Stage 2 · online

Every edit is a transaction.

The developer agent thinks, edits, installs, checks and decides. An install is prepared while the engine keeps stepping, then committed in the gap between two steps, on every GPU rank or on none.

A check counts only if it shows the edited code actually ran.

Stage 2 · online

When the lab falls short, the toolsmith extends it.

A check is too slow, an install fails, the lab falls back to a restart, or the agent enters code the lab does not cover. The online toolsmith prices the new kind of experiment, builds the missing piece and verifies it against a fresh process.

The engine gets more live-editable the longer the agent works on it.

Stage 2 · online

If the engine dies, the lab survives.

A bad edit can hang a rank or leave a sticky CUDA error. The lab marks itself poisoned, refuses further installs, and respawns only the worker group from warm host and GPU caches.

Try it on your machine

The live-lab kernel is pure Python with no dependencies. The toy lab runs on a laptop.

  1. Run the toy lab. Or let your coding agent do it: 
    git clone https://github.com/hao-ai-lab/fastrsi && cd fastrsi
PYTHONPATH=core/livelab python3 -m conformance --lab kernel.toy_lab:ToyLab
  2. Read a recorded walkthrough. Each engine keeps its replayed edits, with real output, under repos/<engine>/examples/.
  3. Bring your own engine. Copy template/livelab/, wire it to the gap between two steps, pass conformance, then follow the offline toolsmith's prompt in core/agents/.
