# FastVideo lessons

Generic lessons from running the FastVideo live lab. Each row: what happened, what to do.

| Lesson | Do |
|---|---|
| FastVideo's `collective_rpc(timeout=...)` does not bound the wait in the multiprocess executor (its `recv` is unbounded, at the pin). A deadline that "times out" there leaves the late reply in the pipe, where the next call would read it as its own. | Poll each worker pipe with your own deadline; after a miss, treat the pipe as dirty until the worker group respawns (`livelab/adapter/lab.py: rank_call`). |
| A host script that builds a `VideoGenerator` at module level crashes with N >= 1 spawned workers: spawn re-imports the main module in every worker. | Keep all work under `if __name__ == "__main__":`. |
| On a shared network filesystem, a client that polls `exists(reply)` for a file another host creates can wait about 30 s (negative lookup cache). | Create the reply file empty before sending the request and poll its contents; each `open` revalidates (close-to-open). Measured: 30 s to 0.12 s per call. |
| The first video after a cold start spent 174 s of 218 s building FlashInfer NVFP4 kernels (`fp4_quantization`, `fp4_gemm_cutlass`) inside the text encoder stage. | Keep one FlashInfer workspace per node and reuse it; a new cache root is a cold start, not a baseline. |
| The FP4 attention path (`h3_vsa_fp4.enabled`) failed at the first forward on the pinned `fastvideo-kernel`: its Python calls an API the installed kernel package lacks. | Check that the installed `fastvideo-kernel` matches the source pin before choosing an attention path; we use BF16 VSA. |
| An edit that adds a `@triton.jit` kernel installed fine, then the next video crashed: Triton reads a kernel's source through `linecache`, which still held the file on disk, so it compiled the base file's lines. | The lab keeps `linecache` equal to the installed text of every module it changed, and puts the file back on undo (`livelab/adapter/agent.py`). Any decorator that reads source at definition time (Triton, Dynamo) needs this. |
| A new top-level `@triton.jit` kernel compiled and ran bit-exact, but its check read `proven: false`: a kernel launch runs no Python, so the witness on the kernel counts 0. | Historical note (now handled by `core/livelab/kernel/jit.py` `R1`, which hooks Triton `pre_run_hooks` for launch witness proof on rebuilt and added top-level `@triton.jit` kernels). For lazily-built kernels inside Python dispatchers, a cached builder also records the Python dispatch. |
| A conformance "startup-only" edit that changed H3's DMD rungs failed in the fresh process: H3 looks up AdaLN modulation in a table precomputed for the trained ladder only. | Pick startup-only edits that stay valid (we use the NVFP4 VAE decoder's decode dtype). |
| An edit inside a module-level `if HAVE_TRITON:` block was refused as `outside_changes`. | Define new functions at the top level; guard inside the function body. |
| Undoing an edit that added a cached Triton-kernel builder (a function holding a nested `@triton.jit` def it built at first call) was refused by the kernel's undo check (`closure_not_restored`, not overridable) and poisoned the lab when the builder's cache still held the nested function. | `core/livelab/kernel/journal.py` now clears cached function attributes, `@functools.lru_cache` wrappers, JIT caches, and container-cached (`tuple`/`list`/`dict`) wrappers on removed definitions and runtime globals/class attributes during undo. If an edit caches closures deeper on an unrelated long-lived engine object, respawn or clear that cache explicitly. |
| Kept edits reinstalled as one diff against base held a function that a later kept edit bypasses (an edit of `MiniMaxH3VSAImpl.tile`, superseded by a direct scatter), so every check read `proven: false` and hid that a new edit on top had run. | Judge each transaction's proof (`check` returns `proven_by_txn`); a judge looks only at the new edit's transaction. |
| A 4-GPU (sequence parallel 4) H3 video differs from the 1- and 2-GPU one (PSNR 17.7 dB), repeatably, with no edit installed. | Keep one golden per GPU count; do not compare across them. |
| A byte-identical copy of a warm JIT cache root at a new path still rebuilt FlashInfer's NVFP4 modules (`fp4_quantization` 72.6 s, `fp4_gemm_cutlass` 86.1 s): FlashInfer runs ninja on every load, and ninja rebuilds when a command line changed; the command lines hold the absolute cache path. Triton's and Inductor's caches (content-keyed) hit after the same copy. | Never copy or move a JIT cache root to "seed" a new slot: keep one root per node and environment at a fixed real path, and put shipped copies back at that path (`livelab/services/jitcache.py: stage_root`; `check_root` reports a moved root before the rebuild). |
| An H3 run on one GPU of a 4-GPU tray read warm videos of 9.0-15.0 s whenever other H3 runs used the tray (ours on the neighbour GPU, the main lab's checks on two others), against 6.0-6.1 s alone; the denoise stage took the hit (5.5 s to 9-11 s), with or without the Triton autotune cache. | Time H3 alone on the tray, or pair every number with a warm video from the same minutes. A parallel run is not a baseline, and our runs slow theirs too. Which shared resource (CPU, host memory, links) is not isolated. |
| A bash job script on the shared filesystem was overwritten (tar extract) while a job ran it: bash, which reads its script as it goes, died with "Stale file handle" between two runs. | Never rewrite a script a running job reads: write each job to a new file name. |
| Fresh-process first video at a warm, path-stable cache still pays per-process work no disk cache holds: Inductor's `torch_key()` hashes every torch source file (0.8-2.6 s), Triton autotunes the VSA kernel (12 benches, about 2 s) unless `TRITON_CACHE_AUTOTUNING=1`, Dynamo traces 5 frames (VAE and the DiT's `@torch.compile` helper), and the text encoder's first call. | Preset `torch_key` from disk and turn autotune caching on (warm restart with path-stable caches, `services/jitcache.py`); for the rest keep the process (in-place rebuild, `adapter/lab.py: rebuild`). |
| The edits the live swap refuses (a constructor, a new field, a module constant) do not need a new process: re-importing the edited module and its importers in the warm worker, swapping the classes of live objects, and merging the constructor's changes into the loaded DiT against meta builds kept weights, CUDA context and JIT state, and gave bit-exact output after a no-op edit and its revert. | Route constructor and module-state edits to `rebuild` before a respawn; a rebuild that would need new weights refuses (`new_submodule`, `new_tensor`) and that edit needs a load. |
| A forkserver zygote that preloaded FastVideo gave workers that could not use CUDA ("Cannot re-initialize CUDA in forked subprocess"): importing `fastvideo_kernel` initializes CUDA at module level (`st_attn_triton.py` builds its autotune configs at import and asks Triton for the current GPU target). | Preload with Triton's target answered from NVML while the server imports (`core/livelab/forksafe.py: pin_triton_target`, called by `livelab/services/zygote.py`), and check `torch.cuda.is_initialized()` in the server before it forks. Upstream fix: build the configs lazily. |
| A fresh process mapped the H3 DiT checkpoint's 1,838 tensors (36.9 GiB) from a holder process by CUDA IPC (`torch.multiprocessing`) in 0.12 s, against 2.5-3.0 s for FastVideo's DiT load from a warm page cache (157 s for the holder's own load to the GPU with `safetensors`). | Weights are not what makes a warm restart slow (imports and per-process JIT are); a holder pays off for the cold path and for the 11-12 s of component loads. |
| A symlink at the cache path did not keep FlashInfer's cache warm after a move: FlashInfer resolves every output path (`flashinfer/jit/cpp_ext.py`, `(output_dir / obj_name).resolve()`), so the ninja files named the link's target, and re-pointing the link rebuilt both NVFP4 modules (155 s). | Keep the real path: stage the copy at the path it was built at; treat a symlinked cache root as a moved one. |
| Importing `flashinfer.jit` touches the CUDA runtime: a forkserver that imported it (our probe's instrumentation) gave workers that could not use CUDA. | Keep FlashInfer (and anything that queries the device) out of the zygote's preload; `zygote.fork_poisoned()` checks before the server forks. |
| A zygote child that dropped an edited module re-imported part of FastVideo and failed: "Duplicate preset registration" (the registry module was kept, its importers re-registered), and the process object's kwargs, unpickled before the refresh, were instances of the old classes. | Refresh in `multiprocessing.spawn.prepare`, before the child unpickles its process object, and drop the whole package when the edit reaches its root (`services/zygote.py`). |
| The first video after an in-place rebuild of a module that keeps per-layer CUDA graphs on its functions ran out of GPU memory: the old functions, still alive, kept their graphs and static buffers (77 GB in graph pools) next to the new code's captures. | Release the state the replaced module objects hold before the new code runs (`rebuild.release_held`: 100 graphs and 62.3 GiB released per rebuild, reserved memory flat); name what cannot be released, with its size. |
| A received CUDA tensor cannot be sent on (torch refuses): a holder that kept the module objects it received could serve the text encoder but not the DiT, whose helper objects held received tensors. | The holder owns a deep copy of what it receives (`copy.deepcopy`, tied tensors stay tied) and serves that. |
| Three of four replayed upstream H3 PRs changed environment-variable defaults (`envs.py`, registered at import) or other module-level code, which the live swap refuses by design. | Expect PRs that touch `envs.py` to need an in-place rebuild of the registry module, not a live swap; price them that way. |
| A replayed PR installed and committed but its witness read 0: the changed code (reference-image VAE encoding) is not reached by the text-to-video workload, so the measurement says nothing about the PR. | Check the witness before reading a replay's timing; replay a PR on a workload that reaches its path. |
| Patches 02-08 installed live one after another and checked once at the end: the first video failed (`triton CompilationError ... StopIteration` in a kernel `_kernel`). Each patch built its Triton kernel lazily on first call; a later patch shifted lines above an earlier patch's builder while `linecache` held only the newest text. Installed with one video after each patch, all 19 went live bit-exact (our 2026-11-19 run). | Fixed in `core/livelab/kernel/swap.py`: nested code objects of swapped and added functions now carry per-version `<fastrsi-live:...>` `linecache` keys restored on undo, so lazily-built nested `@triton.jit` kernels read their own transaction's exact lines even after later swaps shift lines above them. |
| Patch 20 moved the CUDA graphs of patches 15-17 from attributes on two functions into one cache. Installed live on a warm engine that ran 15-17, its first video ran out of memory at 124 frames on 1 GPU: the swap keeps function objects, so the old attributes still held 100 graphs (62 GiB) beside the new cache's 100. | An edit that moves state to a new place releases the old place on first use (patch 20's `_h3_graphs` drops `_graphs_v2` and `_projection_graphs_v1`): 92.6 -> 77.4 GiB allocated, 156.7 -> 84.8 GiB reserved on its first video, bit-exact. |
| An in-place rebuild of all of `patches/h3-hillclimb` (01-20) was refused with `refresh_failed: Duplicate preset registration`: three patches edit `fastvideo.attention.layer` and `fastvideo.distributed.communication_op`, which most of FastVideo imports, so the rebuild re-imported a preset registry. The refusal left the lab at base. A rebuild of the patches that edit only `minimax_h3.py` (15, 16, 17, 20) took 1.12 s, every video bit-exact. | Take edits of widely imported modules by live swap; keep rebuild for modules near the leaves of the import graph. |
| On a newer environment (torch 2.12, CUDA 13) the base H3 video hash was the earlier golden's (`d0e55e892690e260`, 1 and 2 GPUs) but the audio hash was not (`ee49674663eae6e2`, not `29b690c8ac7ae3be`). | Keep goldens per environment as well as per GPU count; compare an edit with a base run in the same environment. |
| With the weights holder, patches 01-19 installed live on 1 GPU ran out of memory at patch 17: until the first respawn the GPU holds the holder's own copy of the weights (30.7 GiB, another process) beside the worker's, and 15-17's graphs leave 156.7 GiB reserved in the worker. Patches 15, 16, 17 and 20 rebuilt in place under the holder fit (77.4 GiB allocated, 85.7 GiB reserved), bit-exact at 124 and 243 frames, and respawns took 3.0-3.5 s. | Budget a holder lab's first worker group for two copies of the weights; take the CUDA-graph patches with patch 20. |
| A lab with the weights holder never exited after its last video (twice): `torch_shm_manager`, which torch's `file_system` sharing starts by fork and exec from the holder, inherited multiprocessing's resource-tracker pipe and outlived the lab, and Python 3.12's tracker finalizer waits for that pipe to close. | Keep the tracker pipe non-inheritable in a process that sets up torch sharing (`services/holder.py: _private_tracker_fd`); find who holds a pipe through `/proc/<pid>/fd` (`grep -F`, the name has brackets). |
