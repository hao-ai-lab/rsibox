# FastVideo lessons

Generic lessons from running the FastVideo live lab. Each row: what happened, what to do.

| Lesson | Do |
|---|---|
| FastVideo's `collective_rpc(timeout=...)` does not bound the wait in the multiprocess executor (its `recv` is unbounded, at the pin). A deadline that "times out" there leaves the late reply in the pipe, where the next call would read it as its own. | Poll each worker pipe with your own deadline; after a miss, treat the pipe as dirty until the worker group respawns (`livelab/adapter/lab.py: rank_call`). |
| A host script that builds a `VideoGenerator` at module level crashes with N >= 1 spawned workers: spawn re-imports the main module in every worker. | Keep all work under `if __name__ == "__main__":`. |
| On a shared network filesystem, a client that polls `exists(reply)` for a file another host creates can wait about 30 s (negative lookup cache). | Create the reply file empty before sending the request and poll its contents; each `open` revalidates (close-to-open). Measured: 30 s to 0.12 s per call. |
| The first video after a cold start spent 174 s of 218 s building FlashInfer NVFP4 kernels (`fp4_quantization`, `fp4_gemm_cutlass`) inside the text encoder stage. | Keep one FlashInfer workspace per node and reuse it; a new cache root is a cold start, not a baseline. |
| The FP4 attention path (`h3_vsa_fp4.enabled`) failed at the first forward on the pinned `fastvideo-kernel`: its Python calls an API the installed kernel package lacks. | Check that the installed `fastvideo-kernel` matches the source pin before choosing an attention path; we use BF16 VSA. |
| An edit that adds a `@triton.jit` kernel installed fine, then the next video crashed: Triton reads a kernel's source through `linecache`, which still held the file on disk, so it compiled the base file's lines. | The lab keeps `linecache` equal to the installed text of every module it changed, and puts the file back on undo (`livelab/adapter/agent.py`). Any decorator that reads source at definition time (Triton, Dynamo) needs this. |
| A new top-level `@triton.jit` kernel compiled and ran bit-exact, but its check read `proven: false`: a kernel launch runs no Python, so the witness on the kernel counts 0. | Build new kernels lazily in a Python function called on every dispatch (a cached builder): the witness then counts the dispatch. A launch counter for Triton targets is not in the kernel yet. |
| A conformance "startup-only" edit that changed H3's DMD rungs failed in the fresh process: H3 looks up AdaLN modulation in a table precomputed for the trained ladder only. | Pick startup-only edits that stay valid (we use the NVFP4 VAE decoder's decode dtype). |
| An edit inside a module-level `if HAVE_TRITON:` block was refused as `outside_changes`. | Define new functions at the top level; guard inside the function body. |
| Undoing an edit that added a cached Triton-kernel builder (a function holding a nested `@triton.jit` def it built at first call) is refused by the kernel's undo check (`closure_not_restored`, not overridable) and poisons the lab: the nested function the edit made is still held, by the builder's cache. | Do not iterate on such an edit with uninstall/reinstall. To revert it: respawn the worker group and reinstall the kept edits (about 45 s respawn + 1 s install, measured). The kernel needs a rule for functions held only by definitions the undo removes. |
| Kept edits reinstalled as one diff against base held a function that a later kept edit bypasses (an edit of `MiniMaxH3VSAImpl.tile`, superseded by a direct scatter), so every check read `proven: false` and hid that a new edit on top had run. | Judge each transaction's proof (`check` returns `proven_by_txn`); a judge looks only at the new edit's transaction. |
| A 4-GPU (sequence parallel 4) H3 video differs from the 1- and 2-GPU one (PSNR 17.7 dB), repeatably, with no edit installed. | Keep one golden per GPU count; do not compare across them. |

| A byte-identical copy of a warm JIT cache root at a new path still rebuilt FlashInfer's NVFP4 modules (`fp4_quantization` 72.6 s, `fp4_gemm_cutlass` 86.1 s): FlashInfer runs ninja on every load, and ninja rebuilds when a command line changed; the command lines hold the absolute cache path. Triton's and Inductor's caches (content-keyed) hit after the same copy. | Never copy or move a JIT cache root to "seed" a new slot: keep one root per node and environment at a fixed path and point every process there (`livelab/services/jitcache.py: env_for`, `check_root` reports a moved root before the rebuild). |
| An H3 run on one GPU of a 4-GPU tray read warm videos of 9.0-15.0 s whenever other H3 runs used the tray (ours on the neighbour GPU, the main lab's checks on two others), against 6.0-6.1 s alone; the denoise stage took the hit (5.5 s to 9-11 s), with or without the Triton autotune cache. | Time H3 alone on the tray, or pair every number with a warm video from the same minutes. A parallel run is not a baseline, and our runs slow theirs too. Which shared resource (CPU, host memory, links) is not isolated. |
| A bash job script on the shared filesystem was overwritten (tar extract) while a job ran it: bash, which reads its script as it goes, died with "Stale file handle" between two runs. | Never rewrite a script a running job reads: write each job to a new file name. |
| Fresh-process first video at a warm, path-stable cache still pays per-process work no disk cache holds: Inductor's `torch_key()` hashes every torch source file (0.8-2.6 s), Triton autotunes the VSA kernel (12 benches, about 2 s) unless `TRITON_CACHE_AUTOTUNING=1`, Dynamo traces 5 frames (VAE and the DiT's `@torch.compile` helper), and the text encoder's first call. | Preset `torch_key` from disk and turn autotune caching on (T2, `services/jitcache.py`); for the rest keep the process (T1 rebuild, `adapter/lab.py: rebuild`). |
| The edits the R0 swap refuses (a constructor, a new field, a module constant) do not need a new process: re-importing the edited module and its importers in the warm worker, swapping the classes of live objects, and merging the constructor's changes into the loaded DiT against meta builds kept weights, CUDA context and JIT state, and gave bit-exact output after a no-op edit and its revert. | Route constructor and module-state edits to `rebuild` before a respawn; a rebuild that would need new weights refuses (`new_submodule`, `new_tensor`) and that edit needs a load. |
| A forkserver zygote that preloaded FastVideo gave workers that could not use CUDA ("Cannot re-initialize CUDA in forked subprocess"): importing `fastvideo_kernel` initializes CUDA at module level (`st_attn_triton.py` builds its autotune configs at import and asks Triton for the current GPU target). | Preload with Triton's target answered from NVML while the server imports (`livelab/services/zygote.py: _pin_triton_target`), and check `torch.cuda.is_initialized()` in the server before it forks. Upstream fix: build the configs lazily. |
| A fresh process mapped the H3 DiT checkpoint's 1,838 tensors (36.9 GiB) from a holder process by CUDA IPC (`torch.multiprocessing`) in 0.12 s, against 2.5-3.0 s for FastVideo's DiT load from a warm page cache (157 s for the holder's own load to the GPU with `safetensors`). | Weights are not what makes a warm restart slow (imports and per-process JIT are); a holder pays off for the cold path and for the 11-12 s of component loads. |
